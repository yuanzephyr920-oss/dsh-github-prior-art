# github-prior-art：先看别人怎么造轮子

**创造性开工前先查 GitHub。** 这不是"建议搜一下"，是开工第一步；跳过它 = 没按流程做。

## 什么时候用

- 从零做：新项目 / 新功能模块 / 新插件 / 新工具 / 新 CLI / 新算法 / 新页面 / 新脚本
- 准备引入一个"应该有人做过"的能力（导出、解析、图表、搜索、鉴权、调度、转换…）
- 用户说"做个 X"，而 X 很可能有成熟开源实现

## 什么时候不用

- 修 bug、小改动、在已有代码里接着写
- 纯配置、纯文档、纯文字/设计任务
- 用户明确说"别搜了，直接写"——照办，但在回答里注明"按你要求跳过检索"

## 第一步：搜（一轮，≤3 分钟）

工具顺序：`gh_repo_search`（它报 `no-token` 就直接走 `web_search site:github.com <词>`，别停）→ `gh_repo` / `gh_file` 读 README → `web_search` 补。

`gh_repo_search` 一次 2–3 组查询，别只搜一组：

- 英文核心词：`markdown table to csv`、`csv converter cli`
- 限定字段：`<关键词> in:name,description,readme stars:>50`
- 生态词：`awesome <领域>`、`<关键词> plugin`
- 中文场景没有通用英文名时，补 `web_search`（如"小红书 图文 生成 开源"）
- 已有工程先看 `package.json` / `requirements.txt` / `Cargo.toml`——可能已经装了

可再查 `gh_search`（issue/PR 里的现成方案）和 npm（`https://registry.npmjs.org/-/v1/search?text=<词>`）。
网络不通时退回 `web_search site:github.com <词>`，别卡在检索上。

## 第二步：挑（3–5 个候选）

每个候选看五件事，用 `gh_repo` / `gh_file` 读 README：

1. **功能重合度**：是不是真干这件事，还是名字像
2. **成熟度**：★ 数、最近提交/发版（半年内？）、issue 是否有人回
3. **许可证**：MIT/Apache/BSD 可商用；GPL/AGPL 不进闭源项目
4. **形态**：库 / CLI / 应用 / 模板——决定能不能嵌
5. **可嵌入度**：语言、运行时、依赖重量；别为一个小功能拖进 200 MB

## 第三步：定（按优先级）

1. **直接依赖**：库、许可 OK、装得上 → 加依赖，写版本
2. **Fork 改造**：很接近但要大改、许可允许 → fork，记改动点
3. **只借结构**：语言/许可/体积不合适 → 读关键文件，抄思路和分层，不抄代码，注明参考链接
4. **自建**：都不合适 → 写一句"为什么不复用"

## 落笔格式（计划或回答里，3–5 行）

```
同类项目：
- owner/repo ★1.2k · MIT · 3 天前 — 可直接依赖，干的就是 X
- owner/repo ★300 · Apache-2.0 · 已归档 — 只参考它的 Y 实现
决定：依赖 A；B 的 Z 结构借鉴，不整体 fork（原因：…）
```

没有高相关就写：`检索无高相关（关键词 …），自建`。

## 反面清单

- 搜了不写结论，直接开写 = 没搜
- 只搜一轮中文就下结论（英文 + 同义词 + awesome 各来一组）
- 拿 star 当唯一标准（归档项目和三个月不动的别碰）
- 把 GPL 代码抄进闭源项目
- 项目里已有依赖还手写一遍
- 无限检索：一轮没有高相关就停，别把开工变成文献综述

## 验证

- 回答/计划里能点名 ≥3 个候选，或明确写"检索无高相关"
- 动手清单里能看到：新增依赖、或参考链接、或"自建理由"
- 用户没看到这几行 = 这步没做
